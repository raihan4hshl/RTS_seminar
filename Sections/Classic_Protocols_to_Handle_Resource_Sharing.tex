It is stated by~\cite{Buttazzo.2024} that the first four protocols, which are mentioned above, have been developed under the fixed priority assignments but some of them have also been extended under the EDF; whereas, the last one is applicale for both fixed and dynamic priority assignments.
\subsection{Non-Preemptive Protocol (NPP)}
A simple design to stop unbounded priority inversion, is the implementation of non-preemptive scheduling. Here, the key idea is to make all critical sections nonpreemptable~\cite{JiacunWang.2017}. A task, which locks the resource gets the highest priority among all the other tasks. After executing at its critical section, the task unlocks the resource. As no task is allowed t o be preempted while it is holding a resource, this protocol is known as nonpreemptive critical section~\cite{JiacunWang.2017}.  In non-preemptive scheduling, once a task starts executing, it cannot be interrupted until it completes or voluntarily yields the CPU. This simplifies resource access since tasks complete before others interfere.
\begin{itemize}
    \item Benefits: 
    \begin{itemize}
        \item No unbounded priority inversion by design.
        \item Simple and easy to implement~\cite{JiacunWang.2017}.
        \item No prior knowledge of resource requirements is needed.
        \item Circular waiting is avoided~\cite{JiacunWang.2017}.
        \item Deadlock is impossible as tasks cannot preempt each other.
    \end{itemize}
    \item Drawbacks:
    \begin{itemize}
        \item High-priority tasks likely to suffer long blocking times (poor responsiveness)
        \item Higher priority tasks can be blocked by any lower priority task arbitrarily even when the higher priority task does not need the resource.
        \item Not suitable for time-critical real-time systems.
    \end{itemize}
\end{itemize}
This protocol ensures that any higher priority task will be blocked, if needed, at most once~\cite{JiacunWang.2017}. Maximum blocking time is equal to the longest critical section length of all the tasks sharing the resource. This means that the worst case occurs ``right after the lower priority task with the longest critical section enters the critical section''~\cite{JiacunWang.2017}. It downgrades the higher priority task to ready and blocked status. According to~\cite{JiacunWang.2017} also, the maximum blocking time of any periodic task is\\
\[
    b_i(\mathrm{rc}) = \max \{ c_k \mid k = i + 1, i + 2, \ldots, n \}
\]
where $c_k$ is the longest critical section length of any periodic task $T_k$. For example, a system with four periodic tasks $T_1$, $T_2$, $T_3$, and $T_4$ with decreasin order priorities can be considered here. The critical section lengths of the tasks are 5, 4, 7, and 3 respectively.\\
\begin{align*}
\text{Maximum blocking time for } T_1: \quad 
& b_1(\mathrm{rc}) = \max \{ c_2, c_3, c_4 \} \\
& = \max \{ 4, 7, 3 \} = 7
\end{align*}
\begin{align*}
\text{Maximum blocking time for } T_2: \quad 
& b_2(\mathrm{rc}) = \max \{ c_3, c_4 \} \\
& = \max \{ 7, 3 \} = 7
\end{align*}
\begin{align*}
\text{Maximum blocking time for } T_3: \quad 
& b_3(\mathrm{rc}) = \max \{ c_4 \} \\
& = \max \{ 3 \} = 3
\end{align*}
Task $T_4$ does not block any other task as it is the lowest priority task. Hence, its maximum blocking time is 0.

\subsection{Priority Inheritance Protocol (PIP)}
According to this protocol, a lower priority task will block a higher priority task and attain the higher priority temporarily. This way, the lower priority task will be able to execute its critical section as soon as possible~\cite{JiacunWang.2017}. According to~\cite{Buttazzo.2024}, ``This prevents medium-priority tasks from preempting $\tau_i$ and prolonging the blocking duration experienced by the higher-priority tasks'', where $\tau_i$ is a set of periodic tasks. The Priority Inheritance Protocol (PIP) is a classic approach to reduce priority inversion in systems where tasks share mutually exclusive resources (e.g., locks, semaphores). When a low-priority task holds a resource required by a higher-priority task, the low-priority task temporarily inherits the higher priority. This prevents it from being preempted by intermediate-priority tasks, allowing it to finish quickly and release the resource.

In the figure~\ref{fig:PIP}, we can see the scheduling of five single-shot task according to PIP protocol. 
    \begin{itemize}
        \item $T_5$ is released at time 0 and start executing.
        \item At time 1, $T_5$ locks the resource X that is free. Occupying the resource, $T_5$ starts executing its critical section.
        \item At time 2, $T_4$ comes in the system. Because, it has the higher priority, it will preempts $T_5$.
        \item $T_4$ completes its execution at time 3 and at the same time $T_3$ is released and it preempts again $T_5$.
        \item At time 4, $T_2$ is released and it preempts $T_3$. Both $T_5$ and $T_3$ are waiting now.
        \item Now, $T_2$ attempts to lock X at time 5 which is held by  $T_5$. So,  $T_2$ gets blocked by  $T_5$ and it inherits  $T_2$`s priority.  $T_5$ starts running causing  $T_2$ and  $T_3$ to wait. 
        \item  $T_1$ is released at time 6 and starts executing by preempting  $T_5$ because of it`s higher priority. Now, $T_2$ $T_3$ and $T_5$ are waiting.
        \item  $T_1$ attempts to lock X at time 7 but the lock is denied because  $T_5$ is holding that.  $T_5$ will inherit $T_1$`s priority by blocking it and starts executing.
        \item $T_5$ completes it`s critical section execution at time 8 and unlocks X. $T_1$ now occupies X. However, $T_5$ still have one unit left to execute.
        \item $T_1$ complete its critical section at time 9 and unlocks X. It will continue executing as it has the highest priority in the system.
        \item At time 10, $T_1$ complete the execution. $T_2$ will be granted to lock X. 
        \item At time 11, $T_2$ locks Y and executes with both X and Y while $T_3$ and $T_5$ are waiting.
        \item At time 12, $T_2$ unlocks X and Y and continues to execute.
        \item At time 13, $T_3$ will start executing after $T_2$ finishes execution.
        \item $T_3$ completes execution and $T_5$ starts.
        \item $T_5$ completes execution at time 15 and thus all tasks are executed.
    \end{itemize}
\begin{itemize}
    \item Benefits: 
    \begin{itemize}
        \item Reduces unbounded priority inversion~\cite{JiacunWang.2017}.
        \item A task can at most be blocked once by any lower priority task~\cite{JiacunWang.2017}.
        \item It is easy to implement as PIP is supported by most of the commercial RTOSs~\cite{JiacunWang.2017}.
    \end{itemize}
    According to ~\cite{JiacunWang.2017}, it was used to solve the famous Mars Pathfinder priority inversion issue in 1997.
    \item Drawbacks:
    \begin{itemize}
        \item It does not prevent deadlock from happening~\cite{JiacunWang.2017}.
        \item A task might fail to meet its deadline as according to~\cite{JiacunWang.2017}, it can be blocked by many lower priority tasks-- causing the blocking time to be too long.
    \end{itemize}
\end{itemize}
\subsection{Priority Ceiling Protocol (PCP)}
The Priority Ceiling Protocol (PCP) is an improvement of PIP which assigns a ceiling priority to each shared resource--- equal to the highest priority of any task that might access it. A task can only lock a resource if it`s priority is higher than the ceiling value of any currently locked resource by another task.
\begin{itemize}
    \item Benefits: 
    \begin{itemize}
        \item Prevents formation of deadlocks by denying those resource requests that, if granted,may cause deadlock later~\cite{JiacunWang.2017}.
        \item Eliminates unbounded priority inversion, and also avoids chained blocking~\cite{JiacunWang.2017}.
    \end{itemize}
    \item Drawbacks:
    \begin{itemize}
        \item It entails overhead of the calculation of resource priority ceiling and system priority ceiling, and the overhead of extra context switches due to priority ceiling blockings~\cite{JiacunWang.2017}.
        \item Eventually, a ``task that does not need to access resources may suffer at most two context switches due to preemption. A task that accesses resource may suffer additional two context switches incurred by blockings''~\cite{JiacunWang.2017}.
    \end{itemize}
\end{itemize}
\subsection{Stack Resource Policy (SRP)}
The Stack Resource Policy (SRP) is a policy which provides stack sharing capacity and simplifies the priority ceiling protocol~\cite{JiacunWang.2017}. The worst-case blocking time of a task is same as PCP under this protocol but this protocol incurs smaller overhead of context switches compared to the priority ceiling protocol~\cite{JiacunWang.2017}. 
\begin{itemize}
    \item Benefits: 
    \begin{itemize}
        \item No unbounded priority inversion~\cite{JiacunWang.2017}.
        \item No deadlock and no chained blocking~\cite{JiacunWang.2017}.
    \end{itemize}
\end{itemize}
